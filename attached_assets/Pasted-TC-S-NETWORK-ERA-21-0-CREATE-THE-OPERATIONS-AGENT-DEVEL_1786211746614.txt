============================================================
ARCHITECTURAL MODEL
============================================================

TC-S now distinguishes three classes of agency:

A. OPERATIONS AGENTS

Network-side functional agents.

They perform authorized work for the TC-S Network.

Examples:

- commissioning
- marketplace operations
- artifact creation
- LifeLens analysis
- energy calculation
- reporting
- fabrication
- settlement
- network administration

This task creates the first general Operations Agent.

B. MEMBER AGENTS

Future persistent agents representing individual human members.

Their role will be:

"Understand my human's intent and represent that intent to the Network."

DO NOT build Member Agents in this task.

C. SYSTEM ORCHESTRATOR / FUTURE REPLICATOR

A future frontier open-weight orchestrator will sit above Operations Agents and UIM.

It will:

- understand intent
- decompose work
- discover capabilities
- delegate to Operations Agents
- assemble results
- verify completion

DO NOT add this new frontier model now.

DO NOT add RunPod inference now.

We are creating the operational substrate it will eventually operate.

============================================================
CORE PRINCIPLE
============================================================

The Operations Agent MUST NOT become a privileged bypass around the existing TC-S architecture.

It must operate through:

UIM
→ Agentic API Surface
→ Policy Engine
→ Executor
→ Existing handlers/services
→ Ledger/database
→ Audit log

The Operations Agent MUST NOT:

- write directly to PostgreSQL
- bypass the Policy Engine
- bypass approval requirements
- mutate balances directly
- circumvent authentication
- invent new network state
- bypass audit logging
- invoke unsupported actions
- silently fall back to direct service calls when policy rejects an action

The ledger/database remains the Network source of truth.

The Operations Agent reasons about state only after reading authoritative state through existing network services.

TASK 5 — CREATE STANDARD UIM INVOKE ENDPOINT
============================================================

Implement:

POST /api/uim/invoke

This MUST be a thin adapter.

It must NOT implement capabilities itself.

Input contract should resemble:

{
  "agent_id": "tcs-operations-agent-v1",
  "capability_id": "QUERY_MARKETPLACE",
  "intent": "Find available solar-powered irrigation artifacts",
  "parameters": {
    ...
  },
  "request_context": {
    ...
  }
}

Required execution path:

1. authenticate caller
2. resolve agent
3. verify agent status
4. resolve capability from Capability Registry
5. confirm status = live
6. confirm uim_exposable = true
7. confirm Operations Agent permission envelope
8. translate capability_id into existing agentic action_type / handler
9. submit through EXISTING Agentic Executor
10. run EXISTING Policy Engine
11. preserve approval requirements
12. execute existing handler/service
13. record normal intent/action/audit records
14. return normalized UIM response

Never invoke handlers directly if doing so bypasses the Agentic Executor.
