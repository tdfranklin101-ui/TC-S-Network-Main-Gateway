TC-S FOUNDY / AUTONOMY SPINE V1 — IMPLEMENTATION TASK

Goal:
Turn the existing commissioning workflow into a reliable “Action Gateway” so agents can operate autonomously inside the TC-S core environment (ledger/wallets/assets/membership/energy metrics) with safe guardrails, audit logs, and deterministic execution.

Context (existing):
- New page: /commission-network.html (4-step wizard)
- It calls: POST /api/agentic/commissioning/create-direct
- Current behavior: submits network spec -> policy engine -> creates pending action request (human approval) -> returns request ID
- There is request tracking / “Check Status”

Deliverables (must all ship in a single PR):
A) ActionRequest persistence layer
B) Action Gateway REST endpoints
C) Policy Engine rules (deterministic, non-LLM)
D) Executor that can actually create a network in the core environment (or a stub that writes to NetworkRegistry if full provisioning is not yet wired)
E) Admin Approval UI (minimal)
F) Smoke test script that exercises end-to-end flow
G) Update/confirm /commission-network.html uses the new endpoints and shows status transitions clearly

Hard requirements:
- Do NOT introduce new cloud dependencies. Use whatever DB/store is already in the repo. If none exists, implement a minimal local store (SQLite/file JSON) behind an interface so it can be swapped later.
- All actions must be idempotent (safe retry). Use idempotency keys.
- Never log secrets/PII. Return safe error messages.
- Keep to existing repo style, routing conventions, and folder structure.

Step 1 — Inventory & align with existing code
1) Locate the backend implementation for:
   - POST /api/agentic/commissioning/create-direct
2) Locate any existing “NetworkRegistry / WalletRegistry / Ledger” persistence mechanisms.
3) Identify existing auth or admin mechanism (cookie, token, env secret). If none, add ADMIN_TOKEN env var check for approval/execute endpoints.

Step 2 — Define ActionRequest model (single canonical structure)
Implement an ActionRequest model with (minimum):
- id (requestId)
- action_type (e.g., COMMISSION_NETWORK)
- actor_type (agent|human|system)
- actor_id (string)
- status: PENDING_APPROVAL | APPROVED | RUNNING | SUCCEEDED | FAILED | REJECTED
- created_at, updated_at
- spec (the submitted NetworkSpec JSON blob)
- policy: { allowed: boolean, checks: [...], warnings: [...], blocked_reasons: [...] }
- result: { network_id?, network_url?, admin_url?, any outputs }
- error: { code, message } (safe)
- idempotency_key
- audit: { trace_id, request_ip? (optional), user_agent? (optional) }

Create a storage interface:
- ActionStore.create(actionRequest)
- ActionStore.get(id)
- ActionStore.update(id, patch)
- ActionStore.listPending(limit)
Pick the existing DB if present; otherwise implement a small JSON file store with locking, or SQLite.

Step 3 — Action Gateway endpoints
Add/confirm these endpoints exist and are wired:
1) POST /api/agentic/actions
   - body: { action_type, spec, actor_id, actor_type, idempotency_key }
   - runs PolicyEngine.validate(spec) and stores ActionRequest in PENDING_APPROVAL if allowed-with-approval
   - returns: { requestId, status, policySummary, checkStatusUrl }

2) GET /api/agentic/actions/:id
   - returns full status + policy + safe result

3) POST /api/agentic/actions/:id/approve
   - requires ADMIN_TOKEN (or existing admin auth)
   - transitions: PENDING_APPROVAL -> APPROVED
   - returns updated action

4) POST /api/agentic/actions/:id/execute
   - requires ADMIN_TOKEN for now (later can be auto-executed by Ops Agent)
   - transitions: APPROVED -> RUNNING -> SUCCEEDED/FAILED
   - calls Executor based on action_type
   - returns result

Backward compatibility:
- Keep POST /api/agentic/commissioning/create-direct working, but refactor it to call POST /api/agentic/actions internally (or alias it cleanly).
- Ensure it returns the same requestId for the UI.

Step 4 — Policy Engine (deterministic)
Implement PolicyEngine.validateNetworkSpec(spec) with explicit checks:
- Commissioning/licensing fiat-only must be true
- taxInclusivePricing must be true
- tcsMicroFee must exist and be >= 0
- token display format must be SW.0000 (or your platform’s required format)
- capabilities list max length 10
- region present
- network name/id present and sane
Return a structured set of checks:
- checks: [{name, pass, detail}]
- warnings: [...]
- blocked_reasons: [...]
PolicyEngine output must be stored in ActionRequest.policy.

Step 5 — Executor: COMMISSION_NETWORK
Implement Executor.executeCommissionNetwork(actionRequest):
Minimum acceptable behavior:
- Write a record to NetworkRegistry (or whatever equivalent exists) using the network id from spec
- Generate and return:
  - network_id
  - network_url (can be placeholder if deployment not wired)
  - admin_url (can be placeholder)
Better behavior (if components exist):
- Provision network resources (db rows, domain mapping, dashboard generation)
- Ensure idempotency: if network already exists with same spec, return existing URLs without duplicating.

Step 6 — Admin Approval UI (minimal but real)
Add a page:
- /admin-actions.html (or existing admin area)
It should:
- List PENDING_APPROVAL ActionRequests
- Show policy check results
- Have Approve and Execute buttons
- Show live updated status and results
No fancy UI required; just functional.

Step 7 — Update commission-network.html wiring
Ensure the wizard:
- On Submit: calls POST /api/agentic/commissioning/create-direct (or /api/agentic/actions)
- Displays requestId and current status
- “Check Status” calls GET /api/agentic/actions/:id and updates UI
- If status becomes SUCCEEDED, show the network_url/admin_url links

Step 8 — Add smoke tests (must run in CI/local)
Create a script (scripts/smoke-actions.sh or equivalent) that:
1) POST create-direct with a valid spec
2) GET action status -> expect PENDING_APPROVAL
3) POST approve (with ADMIN_TOKEN) -> expect APPROVED
4) POST execute -> expect SUCCEEDED
5) GET status -> verify result fields exist
Include an invalid spec test that is BLOCKED/REJECTED with clear policy reasons.

Step 9 — Documentation
Update README or add docs/AUTONOMY.md explaining:
- the ActionRequest lifecycle
- how to approve/execute
- how to add new action types
- how agents should interact (they submit actions, never mutate core directly)

Acceptance criteria:
- All endpoints implemented and reachable.
- UI can create a request and track it.
- Admin UI can approve + execute.
- Smoke test passes.
- No secrets in logs.
- Clear error handling and status transitions.
